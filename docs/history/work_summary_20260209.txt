# 2026년 2월 9일 작업 요약: 최대 생산량 계산기 최적화 시도 및 실패 분석

## 1. 초기 목표
`src/logic/maximizer.ts`의 최대 생산량 계산 로직을 선형 계획법(LP/ILP)으로 전환하여, 기존의 중첩 반복문 방식이 가진 성능 및 정확성 한계를 극복하고, 사용자께서 원하는 높은 재료 입력값에서도 최적의 결과를 빠르고 안정적으로 제공하는 것이 목표였습니다.

## 2. 첫 번째 시도: `javascript-lp-solver` 통합
*   **구현:** `javascript-lp-solver` 라이브러리를 사용하여 `maximizer.ts`를 재작성했습니다.
*   **초기 문제:**
    *   `NaN` 값 반환: `solution.result.crafts`가 `undefined`로 평가되어 `NaN`이 발생했습니다.
    *   로컬 환경에서 페이지 뻗음/멈춤: 모든 재료를 `1234`로 설정했을 때 `solver.Solve(model)` 호출 중 애플리케이션이 멈추는 현상이 발생했습니다.
*   **디버깅 및 해결 시도:**
    *   `TS2307: Cannot find module 'javascript-lp-solver'` 오류: `@types` 패키지 부재로 인한 문제로, `src/types/javascript-lp-solver.d.ts` 파일을 생성하여 해결했습니다.
    *   `ReferenceError: Cannot access 'calculateMaxCrafts' before initialization`: `export const`를 `function ... export { ... }` 형태로 변경하여 호이스팅 문제를 해결했습니다.
    *   `NaN` 문제 재조사: `javascript-lp-solver`의 `solution.result`가 직접 목표 값(숫자)을 반환하는 것을 확인하고, `LPSolution` 인터페이스를 수정하고 `Math.floor(solution.result || 0)`로 접근하도록 변경했습니다.
*   **결과:** 컴파일 오류는 해결되었으나, **계산 시 애플리케이션이 여전히 멈추는 현상**이 발생했습니다. 이는 `javascript-lp-solver`가 중간 규모의 ILP 문제에서도 성능 한계를 보임을 시사했습니다.

## 3. 두 번째 시도: `highs-js` 통합
*   **전환 이유:** `javascript-lp-solver`의 성능 한계로 인해, 더 강력한 WebAssembly 기반 솔버인 `highs-js`로 전환을 결정했습니다.
*   **구현:** `maximizer.ts`를 `highs` 라이브러리를 사용하도록 완전히 재작성했습니다. `calculateMaxCrafts` 함수를 `async`로 변경하고, LP 모델을 `highs`의 문자열 형식에 맞춰 구성했습니다.
*   **문제점:**
    *   **Webpack 폴리필 오류 연쇄:** `highs`가 Node.js 코어 모듈(`fs`, `path`, `process`, `buffer`, `crypto`, `stream`, `vm`, `util`)에 의존하여 `Module not found` 오류가 발생했습니다.
    *   **`config-overrides.js` 설정:** `react-app-rewired`와 `config-overrides.js`를 사용하여 이 모든 폴리필을 추가하는 복잡한 과정을 거쳤습니다.
    *   **`Unterminated string constant` 구문 오류:** `maximizer.ts`의 LP 문자열 초기화 부분에서 발생한 구문 오류를 수정했습니다.
    *   **`TS2552: Cannot find name 'singleCraftRecipe'`:** 구문 오류 수정 후 해결되었습니다.
*   **결과:** 모든 폴리필을 추가하고 `package.json` 스크립트를 수정했음에도 불구하고, `fs` 및 `path` `Module not found` 오류가 지속적으로 발생했습니다. 이는 `highs` 라이브러리가 `create-react-app` 브라우저 환경과 근본적인 비호환성을 가지고 있음을 의미했습니다. `highs`가 `fs` 및 `path`를 Webpack의 폴리필 메커니즘이 처리할 수 없는 방식으로 사용하려 했습니다.

## 4. 결론 및 현재 상태
`highs` 라이브러리는 클라이언트 측 React 환경에 적합하지 않다고 판단되어, 모든 `highs` 관련 변경 사항을 롤백하고 `javascript-lp-solver`를 다시 사용하던 상태로 돌아왔습니다.

현재 애플리케이션은 컴파일 오류는 없지만, **`javascript-lp-solver`를 사용하여 계산을 수행할 때 여전히 페이지가 멈추는 런타임 성능 문제**를 겪고 있습니다. 이는 `javascript-lp-solver`가 사용자께서 원하는 입력값 범위의 ILP 문제를 효율적으로 해결하지 못함을 의미합니다.

# 향후 작업 계획: 실패를 반복하지 않기 위한 치밀한 접근

이번 실패를 통해 클라이언트 측에서 복잡한 정수 선형 계획법(ILP) 문제를 효율적으로 해결하는 것이 매우 어렵다는 교훈을 얻었습니다. 특히 `create-react-app` 환경의 제약과 라이브러리 호환성 문제가 컸습니다.

다음 작업은 더욱 치밀하게 계획하여 사용자께서 원하는 목표를 달성할 수 있도록 하겠습니다.

## 1단계: 현재 상태 롤백 및 안정화 (완료 예정)
*   **목표:** 모든 LP 통합 시도 이전의 안정적인 상태로 되돌리고, 애플리케이션이 오류 없이 빌드 및 실행되는 것을 확인합니다.
*   **세부 계획:**
    *   `git reset --hard <LP 통합 이전 커밋 해시>`를 사용하여 모든 변경 사항을 롤백합니다.
    *   `npm install`을 다시 실행하여 의존성을 정리합니다.
    *   `npm start` 및 `npm run build`를 실행하여 애플리케이션이 정상적으로 작동하는지 확인합니다. (원래의 중첩 반복문 방식 maximizer가 작은 입력에서 작동하는지 확인)

## 2단계: 요구 사항 및 제약 조건 재평가 (사용자 협의 필요)
*   **목표:** 문제 해결을 위한 현실적인 목표와 제약 조건을 명확히 정의합니다.
*   **세부 계획:**
    *   **"최적"의 정의:** 계산 결과가 수학적으로 100% 최적이어야 하는지, 아니면 대부분의 경우에 충분히 정확한 "최선의 노력" 휴리스틱도 허용되는지 사용자께 확인합니다.
    *   **입력값 범위:** 사용자께서 처리하기를 기대하는 재료 입력값의 절대적인 최대치를 다시 한번 명확히 확인합니다. (예: 목재 3만개 이상 등)
    *   **성능 목표:** 계산 완료에 허용 가능한 최대 시간(예: 1초 미만, 5초 미만)을 정의합니다.
    *   **클라이언트 측 vs. 서버 측:** 클라이언트 측에서 해결하는 것이 불가능하거나 비효율적일 경우, Netlify Function과 같은 서버리스 환경에서 계산을 수행하는 방안(서버 측 계산)의 장단점을 논의합니다.

## 3단계: 알고리즘 탐색 및 설계 (클라이언트 측 우선)
*   **목표:** 재평가된 요구 사항을 충족하는 가장 적합한 알고리즘을 탐색하고 설계합니다.
*   **세부 계획:**
    *   **클라이언트 측 휴리스틱 접근:**
        *   **설계:** ILP 솔버 없이, 재료 교환 규칙을 기반으로 빠르고 효율적인 탐욕적(Greedy) 휴리스틱 알고리즘을 설계합니다. 이는 특정 교환(예: 가장 효율적인 교환)에 우선순위를 부여하는 방식이 될 수 있습니다.
        *   **장점:** 구현이 비교적 간단하고 빠릅니다.
        *   **단점:** 수학적으로 완벽하게 최적의 해를 보장하지 않을 수 있습니다.
        *   **검증:** 작은 입력값에 대해 휴리스틱의 정확도를 기존의 (수학적) 최적해와 비교하여 평가합니다.
    *   **휴리스틱이 불충분할 경우 (대안 탐색):**
        *   **옵션 A (클라이언트 측 ILP + 엄격한 입력 제한):** `javascript-lp-solver`가 *더 작은* ILP 문제에 대해서는 작동하므로, 이 솔버가 허용 가능한 성능을 보이는 엄격한 입력 제한을 정의하고 사용자께 제시합니다.
        *   **옵션 B (서버 측 계산):**
            *   **설계:** Netlify Function(Node.js 환경)을 사용하여 ILP 솔버(예: `glpk-js` 또는 `coin-or-utils`와 같은 더 강력한 솔버)를 구현합니다.
            *   **장점:** 브라우저 폴리필 문제 없음, 훨씬 큰 입력 처리 가능, 강력한 솔버 사용 가능.
            *   **단점:** 네트워크 지연 발생, API 호출 필요, 서버 측 로직 추가.

## 4단계: 구현 및 테스트
*   **목표:** 선택된 알고리즘을 구현하고, 정확성, 성능, 사용자 경험을 철저히 검증합니다.
*   **세부 계획:**
    *   선택된 알고리즘을 `src/logic/maximizer.ts`에 구현합니다.
    *   다양한 재료 조합, 특히 사용자께서 제시한 높은 입력값 범위 내에서 철저히 테스트합니다.
    *   UI에 로딩 상태, 오류 처리, 그리고 필요한 경우 입력값 제한 경고 등을 통합하여 사용자 경험을 개선합니다.

이 계획은 이번 실패로부터 얻은 교훈을 바탕으로, 문제의 근본 원인을 해결하고 사용자께서 원하는 안정적이고 효율적인 최대 생산량 계산기를 제공하는 데 초점을 맞출 것입니다.
